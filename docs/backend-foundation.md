# SafetyOS backend foundation

The initial Supabase migration creates empty company-scoped tables, shared catalogues, owner and role assignment tables, and tenant-aware foreign keys. Every application table has RLS enabled and client privileges revoked. No client policies are installed: anonymous and signed-in clients are deliberately denied until the next security milestone. No company, admin, role, plan or module is seeded.

This is **not yet an operational backend**. Company provisioning, live account setup, public portal discovery, anonymous report submission, file storage, RBAC policies, audit event writing and UI data connections are not implemented. Do not use the previews for real data. Supabase Auth uses email/phone identifiers by default; a secure username login flow must be designed and tested without exposing account lookups or storing passwords in application tables. Employees must be able to submit reports without logging in, but public report writes need a constrained server-side endpoint with tenant resolution, abuse protection and privacy safeguards—not direct public table access.

`company_id` alone does not enforce isolation. Future policies and server-side authorization must verify membership, roles and permissions and be tested with multiple tenants. Child foreign keys in the foundation use `(company_id, id)` to prevent cross-company links. Global catalogs and platform owners intentionally have no `company_id`; platform-wide audit events may also have no company.

Next steps: define secure owner bootstrap and admin invitation flow; implement and test RLS for two companies and owner access; add a rate-limited anonymous report ingestion path; implement transactional onboarding and connect the UI incrementally. Storage policies, backup/restore and production email configuration also require separate design and verification.

The `index_foreign_keys` migration adds indexes for foreign keys that were not covered by existing leading index columns. `supabase/tests/foundation_invariants.sql` is a read-only catalog check for foundation-stage client privileges, RLS and foreign-key indexes. It is intentionally specific to the default-deny stage and must be updated when carefully scoped client access is introduced; it does not replace adversarial, multi-tenant authorization tests.

## Admin identity foundation

`company_admins` is an explicit trusted assignment linking a company-scoped user to company-admin access. `current_admin_access()` derives platform-owner status and active company-admin memberships only from `auth.uid()`, and returns no row without an identity. It has a fixed empty search path, accepts no caller-controlled IDs, exposes no table access, and is executable only by the authenticated role. Admin access requires an active assignment, active user and active company. Owner status does not automatically imply company-admin membership. Provisioning and revocation must be performed by a trusted, audited service; the UI must never self-assign ownership or admin status.

This helper is **authorization groundwork, not authentication or route protection by itself**. Supabase Auth must verify sessions server-side; never trust client-decoded JWTs, user metadata, or a company ID supplied by the client. The RPC is not an employee permission system and does not grant access to data. Company data policies and per-action RBAC remain default-deny until designed and tested. Public employee reporting must remain independent of administrator login.

For the requested username/password login, Supabase Auth's password login uses an email or phone identity. A production username flow needs a trusted, rate-limited identity-resolution design, tenant selection and account recovery; do not store passwords or fabricate email addresses. Supabase password reset and owner bootstrap require a verified identity and production redirect/SMTP configuration. No login should be enabled until session handling, role enforcement, revocation, abuse controls, CSRF, recovery and multi-tenant tests are complete.

## Admin sign-in implementation (not production-ready)

The application now includes server-side Supabase password sign-in, an owner email login and a company-scoped username login (company slug + username). The latter resolves the username to the Auth email only in a service-role-only database function. Passwords are verified by Supabase Auth, not stored in application tables. Sign-in checks the verified user and `current_admin_access()` before redirecting. The Next proxy revalidates the user and current admin assignment on protected routes, and denies access on missing configuration or failed checks. Employee routes are not gated. Logout clears the server session cookies. Tables remain default-deny; the admin screens contain no connected tenant data.

Configure the variables listed in `.env.example` through the deployment's secret manager; never send service credentials in chat or commit them. The company login needs a separately provisioned, verified Auth user, active company and user record, active admin assignment and company-scoped username. Platform owner access requires a separately provisioned Auth user and trusted `platform_owners` assignment. No self-service assignment or owner bootstrap is implemented. No accounts or passwords are seeded.

The app has a database-backed global and per-identity throttle, but this is not sufficient production abuse protection: deploy trusted edge/IP rate limiting and bot protection, monitor for account-lockout denial of service, and configure Auth rate limits. Password recovery and invitations require properly configured SMTP, approved redirect URLs, a recovery flow and testing. MFA, session revocation behavior, audit events, concurrent login/rate-limit behavior, actual account provisioning, positive/negative login flows, and cross-tenant authorization need end-to-end testing before production. A protected route alone is not authorization for later data operations: every data query and action must independently enforce company membership and permissions in RLS/server code.

`supabase/tests/admin_isolation_rollback.sql` exercises owner vs company-admin access, two-company separation, membership revocation, inactive users, suspended companies and tenant-aware foreign keys using simulated JWT claims. Test rows are rolled back within a database subtransaction. Run it only in a development or staging database; it does not test real signed JWTs, the sign-in endpoint, application actions or deployed services.

Run `npm test` with Node.js 22 to execute repository tests, including ephemeral PGlite PostgreSQL checks. The database suite applies the checked-in migrations to a fresh in-memory database, verifies default-deny roles and the owner/admin authorization helper, exercises rollback-only multi-company isolation and username resolution, and checks basic login throttling. It uses a minimal local `auth.users`/`auth.uid()` stub, not Supabase Auth or a deployed API. It cannot replace end-to-end tests of real sessions, concurrent rate limiting, RLS policies, browser behavior or production infrastructure.

## Public company portal foundation

`/portal/[company]` resolves a company slug through the anonymous `get_public_portal` RPC with no server secret and no cross-request cache. The RPC returns only the active company's ID, slug and name, and its active locations' IDs, names, region and emergency numbers. Direct public table access remains denied. `company_settings.public_portal_enabled` is false by default; publishing requires an explicit authorized decision because anyone who knows the URL can view those fields. Suspended companies, disabled locations and unpublished companies are excluded. Portal data is not an authorization boundary and cannot grant access to private reports or tenant data. Company names, sites and emergency numbers must not be hardcoded into the application.

A missing configuration, unavailable service, malformed response, invalid slug or unpublished portal produces an unavailable/404 route. Anonymous report submission, live documents, employee data and administrative data access remain unimplemented. The offline queue stores reports locally only and does not send them; it must not be represented as operational reporting. The static manifest still uses a generic root start URL; tenant-aware installation requires separate design. Real JWT/session tests, browser tests, publication approval, environment configuration and deployment are still required.
